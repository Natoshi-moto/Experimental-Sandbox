# Results — first install sweep, 2026-07-23

**status_authority:** `NONE`
**Per `SPEC.md` §4 step 9: real results, not a retroactive rewrite of the plan.**

## What actually happened, in order

1. Fetched and read `install.sh` in full (3,127 lines) before running anything. Traced the one privilege-escalating action (`setuid chmod` on an Electron sandbox helper) to `install_desktop()`, gated behind `INCLUDE_DESKTOP=false` by default — confirmed irrelevant to a CLI-only install. Verdict: clean.
2. **First install attempt failed**: `releases.astral.sh` (where `uv`'s binary lives) resolves IPv6-only, and this environment has no outbound IPv6 route. Not a script problem — confirmed by direct `curl -v` showing "Network is unreachable" on every IPv6 address tried, while IPv4 hosts (GitHub, PyPI) worked fine throughout this whole project.
3. Fix: `pip install --user uv` (via PyPI, IPv4, already confirmed reachable). Re-ran the installer — succeeded cleanly. `hermes-agent==0.19.0` installed, matching the version the unofficial npm bridge referenced during the verification round (a small but real consistency check).
4. `hermes config check` revealed the freshly-scaffolded config was **33 schema versions behind current**. Ran `hermes config migrate` before configuring anything — clean migration, two harmless warnings about unused `teams`/`google_chat` toolsets.
5. Wired DeepSeek (`model.provider=custom`, `model.base_url=https://api.deepseek.com`, `model.key_env=DEEPSEEK_API_KEY`, `model.default=deepseek-v4-flash`) — all four `hermes config set` calls succeeded, matching the schema pulled from the repo's own docs.
6. **Smoke test, DeepSeek path: passed cleanly.** `hermes chat --provider custom --model deepseek-v4-flash -q "..."` → *"I'm DeepSeek V4 Flash, running on the Hermes Agent platform built by Nous Research."* Self-consistent, correct, first try.
7. **Smoke test, local path: three real failures before it worked.**
   - `hf.co/...Huihui-gemma...` (the originally chosen auxiliary model) failed outright: `HTTP 400: does not support thinking`. Confirmed via `ollama show` earlier in this project that this model's capability list never included `thinking` — Hermes sends a thinking/reasoning parameter unconditionally, and Ollama rejects it for models not tagged with that capability. Setting `reasoning_effort: none` on the provider did not bypass this — that field tunes effort level, it doesn't remove the parameter.
   - Switched to `obliterated-gemma:q4` (the other VRAM-safe benchmark candidate, which does list `thinking`). New failure: Ollama had it loaded with only 8,192 tokens of runtime context; Hermes requires 64,000+ for reliable tool use.
   - Setting `providers.<name>.ollama_num_ctx: 65536` and `context_length: 65536` in Hermes config did not change what Ollama actually loaded — Ollama's OpenAI-compatible endpoint doesn't honor a per-request context override this way.
   - Fix (suggested directly by Hermes's own error message, not improvised): baked the context into the model itself via an Ollama Modelfile (`FROM obliterated-gemma:q4` + `PARAMETER num_ctx 65536`), `ollama create obliterated-gemma-65k`. This worked.
8. **Real cost of that fix**: `ollama ps` showed the resulting model loaded at a **40%/60% CPU/GPU split** — 10.1GB of 11GB VRAM used, essentially at the ceiling. The 65,536-token KV cache no longer fits alongside the model weights in this GPU's 11GB. First call (cold load): timed out past 120s. Second call (model already warm): **42.3 seconds** for one short response — versus the ~20s-load/18-23-tok/s standalone `ollama run` benchmark from the verification round, which never exercised the 64K-context requirement Hermes actually enforces.

## What this means

The original model choice (`Huihui-gemma-4-12B...abliterated`, picked for being fastest + largest-context of the VRAM-safe candidates) turned out to be **wrong for this specific role** — not because the earlier benchmark was flawed, but because that benchmark measured something Hermes doesn't actually do (an 8K-context single-shot query), not what Hermes actually needs (64K-context tool-capable). `obliterated-gemma` works but is meaningfully slower once wired in for real, because 64K context plus 11.9B params doesn't fit this GPU's 11GB without partial CPU offload.

## Falsifier check against WHITEPAPER.md §5

The claim as written ("Hermes... can run as a standalone persistent operator process... configured with DeepSeek as its main model and local Ollama models as auxiliary providers") is **partially demonstrated**: DeepSeek path fully passes. Local-auxiliary path passes functionally but not on the "doesn't slow workflow" bar the operator set when choosing a model — 42s for a background compression task is not obviously "doesn't slow workflow," and this wasn't tested under the system's earlier worse memory pressure (10 concurrent Claude Code sessions), only under lighter load.

**Accepted: 42s for the local auxiliary role is satisfactory.** Operator's own words: "42s for a local model reasoning reasonably well is satisfactory to me." `obliterated-gemma-65k` (the Modelfile-derived, 64K-context version) stays as `auxiliary.compression`'s model. Not revisiting this unless real usage shows it's actually a problem in practice, as opposed to a number that looked large in isolation.
